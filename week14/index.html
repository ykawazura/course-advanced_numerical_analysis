    第14回: 並列計算

    今回の目標

    • 共有メモリ並列と分散メモリ並列の違いを説明でき、どちらを使うべきかを問題の規模から判断できるようになる
    • OpenMP の parallel for と reduction を使って、既存の逐次プログラムを数行の追加で並列化できるようになる
    • データ競合（data race）が起きる条件を説明でき、critical / atomic / reduction / スレッドごとの作業領域という4つの対処を使い分けられるようになる
    • 強スケーリング・弱スケーリング・アムダール則（Amdahl's law）を定義し、実測した速度向上を正しく解釈できるようになる
    • 速度向上が頭打ちになる原因——メモリ帯域の壁・負荷の偏り・同期のコスト——を切り分けられるようになる
    • 領域分割と袖（halo）通信の考え方を説明でき、切り方によって通信量がどれだけ変わるかを見積もれるようになる

    「解けるか」から「間に合うか」へ

    第2回から第13回まで、問いは一貫してどう解くかだった。安定か、何次で収束するか、反復は何回で済むか——どれも紙の上で答えの出る問いである。

    ところが第12回で3次元の計算量を見積もったとき、話が変わった。\(N=400\) の3次元拡散を安定条件を満たしながら解くと、更新回数は \(3\times10^{12}\) 回になる。1コアが毎秒 \(10^9\) 回更新できるとして 51 分、実際にはメモリが律速するのでその数倍かかる。しかも \(N=400\) は3次元では決して細かい格子ではない。

    ここで初めて、「アルゴリズムとしては正しいが、このままでは終わらない」という壁に当たる。本回はこの壁への対処である。

    ただし、順序を間違えてはならない。

    • 第10回の SOR は、ヤコビ法の \(O(N^2)\) 回の反復を \(O(N)\) 回に落とした。\(N=64\) で 15284 回 → 241 回、\(63\) 倍である
    • 第13回のスペクトル法は、差分法が数千点を要する精度を数十点で達成した
    • 本回の並列化がこの計算機で稼ぐのは、後で見るとおり 3〜8倍である

    アルゴリズムの改良は桁で効き、並列化は倍率で効く。まずアルゴリズム、次に並列化——この順序は本回を通じて繰り返し確認される。並列化は「遅いプログラムを速くする魔法」ではなく、正しいアルゴリズムを書き終えたあとの最後の一押しである。

    並列計算の2つの形

    並列計算機は、大きく2つに分かれる。

    共有メモリ（shared memory） 分散メモリ（distributed memory）
    実体 1台の中の複数コア ネットワークでつないだ複数台
    メモリ 全コアが同じ空間を見る 各台が自分のメモリしか見えない
    データの受け渡し 変数に書く（自動的に見える） 明示的に送受信する
    標準的な道具 OpenMP MPI（Message Passing Interface）
    プログラムの書き換え 数行の指示行を足すだけ データ構造から書き直す
    規模の上限 1台のコア数（数十〜百程度） 事実上なし（スーパーコンピュータは数万台）
    主な律速 メモリ帯域 通信（帯域とレイテンシ）

    本回は OpenMP を中心に扱い、実測しながら進める。MPI は最終ページで考え方とコード例を示す（実行環境の用意が必要なため、本講義では実行を必須としない）。

    実際の大規模計算では両方を組み合わせる。ノード内は OpenMP、ノード間は MPI というハイブリッド並列が標準的である。どちらか一方を学べば他方の考え方も自然に理解できるので、本回では先に共有メモリで「並列化とは何か」を体で覚え、その上で分散メモリ特有の問題（通信）へ進む。

    再利用する回

    本回には新しい数学がほとんど出てこない。並列化するのは、これまでに書いたプログラムそのものである。

    本章を貫く3つの例題

    例題1: 数値積分による \(\pi\)

    \[ \pi = \int_0^1 \frac{4}{1+x^2}\,dx \;\approx\; h\sum_{i=0}^{n-1} f\!\left(\left(i+\tfrac12\right)h\right), \qquad f(x)=\frac{4}{1+x^2},\quad h=\frac1n \]

    並列化の「Hello, world」である。\(n\) 個の項をどう分担しても、最後に足し合わせれば同じ答えになる——はずである。ところが素朴に書くと答えが合わない。この例題の役割は、\(\pi\) を求めることではなく、共有変数への同時書き込みが何を壊すかを最短で見せることにある。

    さらにこの例題は「うまくいく側」の代表でもある。1点あたり除算を含む十数演算をしてメモリにはほとんど触らないので、演算律速——後で見るヤコビ反復とは正反対の性質をもつ。同じ計算機で 12 スレッドを使ったとき、こちらは 8.28 倍まで伸びる。

    例題2: 2次元ポアソン方程式のヤコビ反復（主役）

    \[ -\nabla^2 u = 2\pi^2\sin\pi x\,\sin\pi y \quad\text{on }(0,1)^2, \qquad u\big|_{\partial\Omega}=0 \]

    第10回の主役をそのまま持ち込む。ヤコビ反復

    \[ u^{(k+1)}_{i,j} =\frac14\left(u^{(k)}_{i-1,j}+u^{(k)}_{i+1,j}+u^{(k)}_{i,j-1}+u^{(k)}_{i,j+1}+h^2f_{i,j}\right) \]

    は右辺がすべて古い値なので、格子点の分担をどう変えても——スレッド数を変えても——結果はビット単位で一致する。第3回で「並列化しやすい」と書いたのは、この性質のことである。

    主役に選んだ理由は、理想的に並列なのに理想的には速くならないからである。逐次で実行される部分はほとんどないのに、この計算機では 8 スレッドで 4.1 倍、12 スレッドではむしろ遅くなる。「並列化率が足りない」では説明できないこの現象の正体を突き止めるのが、2ページ目の主題である。

    例題3: 1次元拡散方程式の領域分割

    \[ \frac{\partial u}{\partial t}=\alpha\frac{\partial^2u}{\partial x^2}, \qquad u(x,0)=\sin\pi x,\quad u(0,t)=u(1,t)=0 \]

    第9回の FTCS を、格子を \(P\) 個の区間に切って解く。各区間は「自分の担当ぶん＋左右に1点ずつの袖（halo）」を持ち、毎ステップ袖に隣の端の値を写してから更新する。

    この例題は分散メモリの雛形である。袖を毎ステップ交換すれば分割しない計算と完全に一致し、交換を忘れるとプログラムは止まらずにそれらしい形の間違った解を返す。3ページ目では、この構造の上で「どう切ると通信が少ないか」を見積もる。

    OpenMP を使うためのビルド設定

    OpenMP はコンパイラの機能なので、環境ごとに指定が違う。

    • Visual Studio: プロジェクトのプロパティで「C/C++ → 言語 → OpenMP のサポート」を「はい（/openmp）」にする。コマンドラインからは cl /O2 /openmp prog.c
    • Linux / Docker（gcc）: gcc -O2 -fopenmp prog.c -o prog -lm
    • macOS（Apple clang）: 素の状態では OpenMP に対応していない。Homebrew で brew install libomp を入れたうえで 
      cc -O2 -std=c11 -Xpreprocessor -fopenmp -I$(brew --prefix libomp)/include \
   prog.c -o prog -L$(brew --prefix libomp)/lib -lomp -lm

    #include <omp.h> を書いたのにこれらの指定を忘れると、指示行が単なるコメントとして無視され、逐次のまま何ごともなく動く。「並列化したのに1倍のままだ」というときは、まずこれを疑うこと。

    なお、omp_get_num_threads() などの関数を使う場合は、OpenMP が有効かどうかで #ifdef _OPENMP を切り替えると、どちらの環境でもコンパイルが通るプログラムになる。

    本回の測定値について

    以降に載せる時間・速度向上は、すべて Apple M2 Max（論理コア 12＝性能コア 8＋効率コア 4）での実測値である。同じプログラムでも、計算機が違えば数字は変わる。

    特に、この計算機は性能の違うコアが混在しているため、速度向上がスレッド数に対して単調にすらならない。皆さんの環境で違う数字が出たら、それは失敗ではない。数字そのものではなく、「どこで頭打ちになるか」「どのカーネルがよく伸びるか」という傾向を読み取ること。
